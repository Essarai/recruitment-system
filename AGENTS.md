# Prototype Instructions

Run the local server yourself and open the preview in the browser available to this environment. Do not give the user server-start instructions when you can run it.

Before making substantial visual changes, use the Product Design plugin's `get-context` skill when the visual source is unclear or no longer matches the current goal. When the user gives durable prototype-specific design feedback, preferences, or decisions, record them in `AGENTS.md`.

When implementing from a selected generated mock, treat that image as the source of truth for layout, component anatomy, density, spacing, color, typography, visible content, and hierarchy.

Build app UI in `src/`. Keep `.openai/hosting.json`, `worker/index.js`, `scripts/prepare-sites-build.mjs`, and `tests/sites-worker.test.mjs` intact so the same local prototype can be handed to Sites. Before a Sites handoff, run `npm run build` and `npm run test:sites`; the build must leave `dist/client/index.html`, `dist/server/index.js`, and `dist/.openai/hosting.json`.

Product rules confirmed 2026-10-17: candidate education is required from the nine specified categories; validate mainland mobile/email formats; new application job snapshots the selected workflow name; a candidate with any ongoing application cannot create another. File preview/download access uses short-lived authorized presigned URLs. Preserve historical applications when templates are renamed.

Resume library design: keep the approved Google-style restrained typography and blue/gray palette. Show workflow/job and actual interview round in separate columns, including arrangement/feedback state. The actions column contains actions only; hide create-application while any application is ongoing rather than showing a disabled status button. Prefer the active application and retain accessible history.

Typography: one shared system font stack and a 24 / 20 / 14 / 12 px scale for page titles, dialog/section titles, body and controls, and captions. Do not change type sizes per page or breakpoint; use spacing and wrapping for responsive layouts. Heading weights 500/600, body/actions 400, secondary captions 400.

Recruitment workflow confirmed 2026-10-18: only the first round requires resume acceptance. HR saves and pushes the resume to a selected business interviewer; this person may view it before scheduling and accept or return with a reason. HR schedules the first round only after acceptance and with that interviewer. Later rounds retain direct HR scheduling. Declining a resume immediately terminates this application. Preserve existing scheduled legacy interviews without retroactive acceptance.

Resume preview preference confirmed 2026-10-18: open PDFs directly in the browser's native reader in a new tab. Use the authenticated resume redirect to freshly signed private URLs; do not embed a custom PDF renderer or expose persistent public object URLs. Word stays an attachment download.

PDF import autofill: extract text on the backend locally, without sending resumes to third-party AI. Fill only empty, unedited fields and keep HR review before save/push. Never infer the nine education categories from degree or university names; only fill an explicit exact category and otherwise ask HR to confirm. Changing files removes untouched values auto-filled from the previous file; stale parsing responses must not affect the new file. Scanned/encrypted/unsupported PDFs fall back to manual entry. Keep native browser preview separate from backend PDF text extraction.

Page roles confirmed 2026-10-18: application list is the work queue for advancing each application, with one consistent View Details action and feedback/scheduling information. Resume library is one row per candidate, emphasizing profile, application count and resume versions; current progress is a short summary only. Candidate archives show every past/current application with its own resume and an explicit link into the application workflow. Keep scheduling and result actions out of the archive. Existing active-application duplicate guard still applies.

Progress color preference confirmed 2026-10-18: use consistent text badges across application list, candidate library/archive and interview rounds. Amber for awaiting action/scheduling/HR decision; blue for scheduled interviews; purple for awaiting feedback; green for submitted feedback/company hiring decision; red for returned/rejected; gray for canceled/withdrawn. Keep text labels and existing typography.

Interview dialogue and MCP confirmed 2026-10-18: each interviewer may optionally attach one complete dialogue document (UTF-8 TXT/Markdown, PDF, DOC/DOCX, up to 20 MB) to their own feedback. Save attachments with drafts; keep drafts and their attachments private to the interviewer. HR may access submitted feedback attachments, including preserved formal versions. Formal feedback stays locked until HR returns it. The interviewer sidebar has a separate MCP entry immediately below My Interviews, opening a dedicated read-only personal Streamable HTTP MCP connection page with one active 30-day token per account, shown once, hashed in MySQL, revocable/resettable and invalidated on password changes. MCP exposes only own interviews, own feedback and authorized short-lived file links; no HR notes, other interviewers' feedback, business writes or automatic submission. Connection tutorial explains custom Bearer headers, localhost versus deployed HTTPS access, and OAuth-client limits.

MCP navigation clarified 2026-10-18: MCP is a standalone interviewer sidebar destination directly below My Interviews; do not embed its connection/token/tutorial controls in the interview list.

Application progress clarified 2026-10-18: the application list uses a segmented progress bar with text for resume confirmation, each actual workflow round, and final result. Mark a round complete only after submitted feedback; elapsed time or a later scheduled round must never fill an earlier missing-feedback segment. Ending an application completes only the result node and preserves actual incomplete interview segments.

Pagination confirmed 2026-10-18: use the same pagination controls for application list, resume library, candidate application history, account list, workflow templates, interviewer screening queue and scheduled interviews, interview arrangements and operation history. Default 10 rows, selectable 20/50; filter/search resets to page one, shrinking results clamps to a valid page. Paginate display collections only; never slice the data used by workflow permissions, totals, duplicate guards or editing forms. Current state API still loads the authorized aggregate; this is UI pagination, not server-side fetching.

Application termination clarified 2026-10-18: every application-list row uses 查看详情. Display only 进行中 / 已录用 / 流程终止 as overall states. A declined resume or any formally submitted negative interview feedback immediately terminates the current application; drafts do not. Preserve reasons and history, cancel future unsubmitted arrangements, and forbid reopening or resending ended records. Recall an existing candidate only from the resume library with 重新捞起, creating a new application and retaining prior history. Startup corrects ongoing records with an explicit existing negative decision, without overwriting already ended/hired records.

Action sizing clarified 2026-10-18: repeated list/detail row actions such as 查看详情 use compact 28 px controls with 3 px vertical / 10 px horizontal padding and the shared 14 px body type. Keep page-level primary actions and dialog submissions at their established size.

List action style confirmed 2026-10-18: application-list actions use the same borderless blue text-button style as the resume library, including its compact spacing and shared type scale.

Resume library columns clarified 2026-10-18: reserve a fixed 276 px action column and keep archive/edit/recall actions in a single horizontal row. Allocate 20% to candidate details, 22% to contact details, 150 px to attachments, and remaining space to application summary; use horizontal table scrolling on narrow screens instead of wrapping actions.

MCP preset workflow confirmed 2026-10-18: provide a one-click Codex setup and evaluation prompt. Match the user-selected candidate/round, ask on ambiguity, use actual interview evidence, and preview all fields/files before each write. Optional newly issued write-enabled tokens expose only save_my_feedback_draft and upload_my_transcript for own unlocked rounds; existing tokens remain read-only. No MCP formal submission, screening decisions, hiring decisions or HR writes. Browser and MCP must share feedback/file validation and ownership checks. Codex config follows the official Streamable HTTP http_headers setting; connection may require a client reload.

User explicitly requested 2026-10-18: copied MCP preset prompts include the current personal Token for one-step Codex configuration. Clearly label the credential-bearing content, keep it only in current React state (never browser storage), and require explicit Token regeneration after reload; never silently reset. Configure only the matching personal Codex MCP section and protect the local config, without echoing or committing the Token.

MCP copy ordering clarified 2026-10-18: users must explicitly create a Token in the current page before copying the preset; fill its token placeholder from that newly returned secret. Do not offer manual Token pasting. Copy stays disabled after reload/revoke until explicit creation; recreating invalidates the previous Token and must be clearly labeled.

Resume recall and updates confirmed 2026-10-18: recalling from the library lists existing private resume versions, defaults to the most recent and requires no re-upload. Provide 更新简历 on the candidate library/archive, which appends a candidate-level version without creating an application or replacing any application snapshot. Preserve all versions, count distinct file IDs, and allow HR-only access to candidate-level attachments; interviewers still access only their authorized application snapshot. Keep all four library actions horizontal with sufficient action-column width.

Workflow JD confirmed 2026-10-18: workflow create/edit has an optional plain-text JD (20,000 characters max). Snapshot it on new applications so later template edits do not rewrite history. Show it in workflow/application/feedback details and expose only through existing authorized MCP details. Keep legacy records without JD unchanged.

Interviewer page grouping confirmed 2026-10-18: 我的面试 shows one collapsible parent record per candidate ID, never by name. Group separate applications and own scheduled rounds as child records, and place first-round resume confirmation inside the matching application instead of a separate repeated queue. Keep per-application resume/JD and per-round feedback targets, canceled/locked behavior, candidate search and pagination (by candidates). Show only actionable pending confirmations and due/returned unsubmitted feedback in parent badges; future appointments are not automatically completed or overdue.

Interviewer actionable work clarified 2026-10-18: 我的面试 defaults to 待我处理. Expose each pending resume confirmation and due/draft/returned feedback task with job, round, reason and direct action outside any collapsed details. Keep one candidate parent and fold complete history underneath. Provide 即将面试 and 全部候选人 views with exact item counts. Waiting-for-HR, canceled and submitted records are not interviewer to-dos; elapsed time is a prompt to verify actual completion, never proof. Preserve draft/returned tasks even before their scheduled time.

Typography consolidation confirmed 2026-10-18: all form/navigation/action controls stay at shared 14 px even inside 12 px caption containers; remove font:inherit resets that accidentally shrink controls. Candidate identities in HR/interviewer lists use 14 px medium rather than section-title styling. Page/section/dialog titles retain 24/20 px, helper/status/count copy 12 px; code/config samples share a deliberate monospace token. Keep responsive type sizes unchanged.
