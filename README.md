# 招聘工作台

React + Vite 前端，Node.js / Express 后端，已连接用户提供的 Railway MySQL 和 MinIO（S3 兼容存储）。运行时不再加载 mock 候选人、演示账号或浏览器本地数据库。

## 当前使用

本地页面：http://localhost:4173/ 。API：http://127.0.0.1:3001/（仅本机监听）。初始账号为 `admin`，随机初始密码位于本目录 `INITIAL_LOGIN.txt`（0600，仅本机可读，已排除版本控制）。首次登录后可以从右上角修改密码；修改后全部旧会话失效。

首次业务使用顺序：

1. HR 从“账号管理”创建真实面试官账号。
2. 从“流程设置”创建流程，可为每轮指定默认面试官。
3. 导入候选人简历，创建应聘并安排面试。
4. 面试官用独立账号填写本人面评，由 HR 推进或结束应聘。

业务数据初始为空。旧浏览器演示数据不迁入 MySQL，成功登录后会清理当前来源下名为 `light-recruitment-v1` 的旧演示数据库。测试样例只留在 `tests/fixtures.js`，不会导入运行页面或数据库。

## 服务配置

`.env` 为本机后端配置（0600，已忽略），包含既有 MySQL / MinIO 连接信息。`.env.example` 是无秘密示例。禁止把这些变量改成 `VITE_` 变量或打包进前端。

- MySQL：使用用户提供的专属 CA 验证，CA 位于 `server/certs/mysql-ca.pem`。该实例自动证书不包含公网代理域名，当前校验 CA、不校验代理主机名；没有关闭 CA 验证。
- MinIO：私有 Bucket `recruitment-resumes-20261017`；简历使用 UUID 对象 key，不覆盖旧版本。浏览器通过鉴权 API 上传与读取，拿不到存储密钥。
- 业务表：`recruitment_users`、`recruitment_sessions`、`recruitment_state`、`recruitment_files`、`recruitment_audit`。初始化只创建本应用表，不清空既有服务或其他项目数据。

## 数据与权限

- 密码使用 scrypt 随机盐哈希；随机会话 token 的哈希存入 MySQL。Cookie 为 HttpOnly + SameSite=Strict，8 小时有效。生产 HTTPS 下开启 Secure。
- HR 读取全库及正式面评，草稿正文不返回 HR；HR 退回时保留旧正式版本。
- 面试官仅接收本人已安排的轮次与关联候选人、本人面评，无 HR 备注、他人面评、其他应聘记录。
- 服务端验证角色、输入、流程与面评状态，拒绝 HR 代录或清除面评，文件读取按关联应聘权限检查。
- 每次保存携带 revision，在 MySQL 事务内锁定并校验，防止多人静默覆盖；冲突时提示刷新重试。当前适用约 20 人、1,000 份简历的规模：业务聚合保存在一个 JSON 状态行，账号、会话、附件和审计独立表。后续需要更高并发或报表时再拆分业务表。
- PDF/DOC/DOCX 上传上限 20 MB，服务端验证文件名、大小及文件头。PDF 在线预览，Word 下载。没有病毒扫描与 Office 深度解包验证。
- 上传成功但表单保存失败时，未关联附件会留在私有存储；暂未实现孤立附件定时清理。

## 开发与部署

```sh
npm install
npm run server
npm run dev -- --host 127.0.0.1 --port 4173 --strictPort
npm test
npm run build
npm run test:integration
```

开发时 Vite 将 `/api` 代理到 3001。生产使用 `npm run build` 后运行 `npm start`，同一 Node 服务提供前端和 API。Railway 设置构建命令 `npm run build`、启动命令 `npm start`，通过服务端变量提供配置，并设置 `NODE_ENV=production`、`API_HOST=0.0.0.0`、`COOKIE_SECURE=true`、`PUBLIC_ORIGIN=https://你的应用域名`。Railway 的 `PORT` 优先于本机 `API_PORT`。

同项目环境部署可切换已提供的 MySQL / MinIO 私网地址；公网预览链接只供本机开发使用。本轮没有部署线上应用，也没有配置其他域名。

原有 Sites 静态构建相关文件保留供设计模板兼容，但正式系统依赖此 Node 后端，不能只上传静态前端到 Sites 就运行数据库功能。

## 验证

`npm test` 覆盖业务规则、账号密码、权限数据裁剪、上传校验、HR 修改限制和构建打包。`npm run test:integration` 使用实际 MySQL 与 MinIO 验证登录、持久化、上传/下载、私有对象、越权拒绝、revision 冲突、草稿/提交/退回及应聘结果；临时账号、候选人、流程、附件和对象在结束后清理，只保留正式管理员。

首次空库只有一个 HR 管理员，无候选人、应聘、面试官或流程模板。自动建表采用 CREATE TABLE IF NOT EXISTS；后续结构变更应通过迁移处理。数据库备份、服务监控、账号禁用/密码找回和恶意文件扫描尚未接入。凭据轮换与账户权限调整需按实际运维安排。

## 2026-10-17 录入与附件规则更新

- 手机号填写时校验中国大陆 11 位手机号码；邮箱填写时校验常见邮箱格式；两者至少一项。前后端共同校验，不验证号码或邮箱的实际归属。
- 学历为必填下拉：双九硕、单九硕、双二硕、单二硕、双非硕、九本、211本、普本、大专。历史记录不自动推断分类；编辑资料或再次应聘时需补齐。未编辑的旧记录不阻碍其他候选人的正常操作。
- 新应聘选择流程后，岗位直接保存为该流程名称，同时保存 templateId；不再手填岗位。流程重命名不修改历史应聘的岗位。
- 同一候选人只允许一条进行中的应聘。简历库和详情的创建入口禁用，重复候选人复用时同样检查；后端在事务与 revision 检查下拒绝重复创建。结束已有应聘后允许再次应聘。
- 附件预览、下载通过 `/api/resumes/:id/url`：服务端先鉴权，再返回有效期 300 秒的预签名 GET URL。旧文件接口鉴权后重定向至相同机制。PDF 设置 inline，在新标签页交给浏览器自带阅读器预览；Word 为 attachment 下载。长期只保存对象 key，不保存临时 URL。
- 上传仍通过后端验证文件内容后写入私有存储。预签名 URL 在有效期内持有者可访问，过期后重新点击会签发新链接。

## 2026-10-18 首轮简历确认

新应聘录入时选择首轮业务面试官，保存后推送简历。面试官可在“首轮推荐简历”中查看附件，选择接受面试或填写不通过原因。接受后 HR 才能安排首轮时间、会议链接，且安排给接受人；后续轮次直接由 HR 安排，无需重复接受。HR 可在首轮尚未安排时更换确认人，重新推送后需重新接受。简历筛选不通过会立即终止本次应聘。尚未排期的历史应聘先由 HR 推送，已有首轮排期的历史记录保持原有行为。推荐简历只向指定面试官开放；未安排时间不代表任何面试官都可以访问。推送后已登录的面试官可点击“刷新列表”获取最新推荐。

PDF 使用浏览器原生阅读器。点击简历时同步打开新标签页，由同源附件接口鉴权后重定向至新签发的 5 分钟预签名 URL；不经过前端 fetch 或 PDF.js。原页面保留，Word 下载也不会替换招聘系统页面。浏览器未启用 PDF 阅读器时可能转为下载。此方式避开脚本跨域读取限制，但仍受外网到对象存储的连接质量影响。

## PDF 上传自动回填

HR 选择 PDF 后，将文件发到仅 HR 可用的 `/api/resumes/parse`。后端使用 PDF.js 在独立工作线程读取文字，不使用第三方 AI 或 OCR。要求 Node 22.13 或更新版本。提取方式参照 [PDF.js 官方 Node 示例](https://github.com/mozilla/pdf.js/blob/master/examples/node/getinfo.mjs)，浏览器原生预览不受影响。

识别明确的姓名、唯一手机号/邮箱、标注年龄、工作年限、现任公司、当前职位及现居城市。仅回填未手动编辑的空白项；换文件清除上一份未修改的自动值。保留原有候选人资料，不根据日期推断年龄或任职年限。学历只有原文明确写出九种分类之一才自动选择；普通硕士、本科等提示 HR 确认，不依据学校推断。岗位仍来自所选流程。

解析不写入 MySQL 或对象存储；HR 核对并保存后才正式上传附件、保存应聘并推送。仅读取前 20 页、20 万字，解析限时 15 秒，工作线程堆内存 256 MB，同时最多 2 个任务。扫描件、损坏、加密或超限文件提示手动填写。规则识别不保证覆盖所有简历版式，结果须人工核对。

## 应聘列表与简历库的分工

应聘列表按应聘记录处理招聘：展示当前进度、未交面评、总体结果，并按实际状态提供推送、首轮安排、查看安排、后续排期或记录结果的入口。已过时间的欠交面评仍保留，且不阻止安排下一轮。

简历库按候选人查找档案：展示联系方式、应聘次数和简历版本，仅保留简短进度摘要。查看档案可集中查阅所有应聘及其独立简历；需要排期或记录结果时，通过“前往应聘”切换到应聘列表处理。有进行中应聘的候选人不显示创建新应聘入口。

### 面试对话附件与个人 MCP

面试官填写面评时可选附一份完整面试对话，支持 UTF-8 TXT、Markdown、PDF、DOC、DOCX（20 MB 以内）。附件跟随草稿保存，草稿对 HR 隐藏；正式提交后锁定，HR 可预览 PDF 或下载文件。移除/替换只影响当前草稿的引用，已保留的正式版本不会被覆盖。文件保存在既有私有 MinIO，访问链接有效 5 分钟。未保存的上传文件与被替换的旧文件暂不自动清理，避免误删历史资料；需要回收时应按业务引用核对。

面试官侧边栏的“我的面试”下方有独立的 **MCP** 入口，连接地址、Token 管理与教程集中在此页面。面试官可生成个人 Token（30 天有效，仅生成时显示），重置会立即替换旧 Token，也可主动撤销。数据库只存 SHA-256 摘要；修改密码同时撤销 Token。启动时增量创建 `recruitment_mcp_tokens` 和 `recruitment_transcripts`，不改写已有招聘数据。

MCP 地址为 `PUBLIC_ORIGIN` 下的 `/mcp`，采用官方 MCP SDK 的无状态 Streamable HTTP（JSON 响应）。本地 Vite 已代理 `/mcp` 到 API。部署时设置 `PUBLIC_ORIGIN` 为真实 HTTPS 外部地址，反向代理 `/mcp` 到同一 Node 服务，并保留 `Authorization`、`Accept`、`MCP-Protocol-Version` 请求头。不要将长期 Token 放进 URL。当前个人 Token 模式适用于支持自定义 Bearer 请求头的客户端，尚未实现 OAuth 授权和旧版 SSE。

在支持此连接方式的客户端中添加服务地址，请求头设置为 `Authorization: Bearer <个人Token>`。例如将以下配置合并到个人 `~/.cursor/mcp.json`（不要提交至共享仓库）：

```json
{
  "mcpServers": {
    "my-interviews": {
      "url": "http://localhost:4173/mcp",
      "headers": {"Authorization": "Bearer <替换为个人Token>"}
    }
  }
}
```

客户端应显示三个工具：

| 工具 | 内容 |
| --- | --- |
| `list_my_interviews` | 本人待确认简历及已安排/历史面试；`offset`、`limit` 分页，返回 `total` |
| `get_my_interview` | 按 `applicationId` 读取候选人资料、本人轮次及本人面评（含草稿）；不含 HR 备注与其他人的面评 |
| `get_interview_file` | 按 `applicationId`、`kind=resume/transcript` 返回 5 分钟文件链接；对话需传本人 `roundId` |

AI 仅辅助准备和整理，正式面评仍由面试官在页面核对提交。客户端如何读取临时文件链接取决于其文件下载能力。Token 撤销后新请求立即失效，已经签发的文件链接最多仍有效 5 分钟。云端客户端无法访问用户电脑的 localhost，需要已部署、可访问的 HTTPS 地址。

参考：[MCP SDK Streamable HTTP](https://ts.sdk.modelcontextprotocol.io/server)、[Cursor MCP 配置](https://prod.cursor.com/help/customization/mcp)。

## 列表分页

所有业务列表统一支持每页 10 / 20 / 50 条、总条数、当前范围及前后翻页。覆盖应聘列表、简历库、候选人应聘历史、账号、流程模板、我的面试、首轮推荐、面试安排和操作记录。搜索或筛选后回到第一页，结果减少时自动限制到有效页。分页只切分展示集合；权限、重复应聘判断、流程推进和统计仍使用完整数据。当前为前端分页，`/api/state` 仍一次返回本人有权读取的完整聚合数据。

应聘列表统一通过“查看详情”处理，整体状态为进行中、已录用、流程终止。任一轮正式面评不通过也会终止本次流程，草稿不触发终止。终止后不能重推或继续排期；同一候选人再次考虑时，从简历库“重新捞起”，建立独立应聘并保留历史。启动时自动纠正仍在进行中但已有明确不通过结论的旧记录。

### Codex 预设提示词与面评草稿

面试官 MCP 页面可一键复制预设提示词（含当前服务地址和当前个人 Token，仅交给信任的客户端）。Codex 合并个人 MCP 配置后，列出面试并匹配用户指定的候选人/轮次；目标不明确时先询问。仅根据实际面试证据整理评价，先展示字段和附件，用户确认后保存草稿与上传对话，最终正式提交由面试官在页面完成。配置可能需要重载客户端。

默认及已有 Token 仍只读。勾选“允许保存本人面评草稿和上传对话”后生成/重置 Token 才启用两个写工具：`save_my_feedback_draft`（需要最新 revision，冲突不覆盖）及 `upload_my_transcript`（标准 base64，TXT/MD/PDF/DOC/DOCX，20 MB 内，随后用 transcriptId 关联草稿）。写工具要求逐次 confirmed=true，客户端须先取得用户明确确认；服务端校验本人、有效安排、锁定和附件归属，不代替客户端确认界面。MCP 不提供正式提交或招聘结果决策工具。数据库启动时为 Token 增加默认 false 的 can_write 字段，无新增部署变量。

Codex 官方配置说明：https://developers.openai.com/codex/mcp/

用户明确选择将 Token 放入复制提示词：页面生成后可直接复制；刷新后需主动重新创建 Token 才能复制（旧 Token 随之失效），不从数据库取回明文、不写入浏览器本地存储。预设使用 Codex 官方 http_headers 配置，仅存个人配置文件并限制文件权限。

页面顺序为先创建个人 Token，再复制带该 Token 的预设提示词；不提供手动粘贴旧 Token 的入口，明文只在本次创建后的页面内存中使用。

简历库支持“更新简历”独立追加候选人简历版本，不创建应聘、不覆盖历史或进行中应聘的附件。重新捞起默认复用历史简历，也可选择其他历史版本或上传新文件。候选人档案统一展示去重后的简历版本；新版本仅 HR 可访问，面试官仍只能访问本人获授权应聘中的附件。候选人版本保存在现有 JSON 聚合中，无新增部署变量。

流程创建和编辑支持选填 JD（最多 20,000 字符）；新应聘保存当时 JD 快照，后续编辑流程不会改写已有应聘。HR 详情、面评填写和本人 MCP 详情可查看对应 JD。旧记录保持不变，不追溯补写。
